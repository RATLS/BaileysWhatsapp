Start here / The cast

Seven jobs, explained like a team

Each part has one main responsibility. You can understand the whole system before learning its tools.

▦

Dashboard · the control room

A web page where a person creates accounts, checks their connection, sees waiting messages, and reads history.

◇

Proxy · the front door

Receives secure web traffic and passes it to the API. The project uses Nginx for this job.

◈

API · the receptionist

Accepts requests, checks that they make sense, and writes work orders. It does not hold a WhatsApp connection.

⬡

Redis · the shared notebook

Keeps client status, waiting messages, work orders, and recent updates where the API and worker can both find them.

⚙

Worker · the operator

Owns each WhatsApp connection and sends waiting messages, one at a time. Baileys is the library it uses to talk to WhatsApp.

▤

Storage · the memory

Session files remember a WhatsApp login. Log files keep message history. Docker runs these parts in separate containers.

⚑

Alerter · the night watch

Keeps an eye on the accounts you picked and posts in the team’s Google Chat space when one goes offline, gets stuck, or keeps failing — and again when it is fine.

The essential idea: asking the API to send a message means “put this in the waiting line.” The worker sends it when that WhatsApp account is connected. A client here is one managed WhatsApp account, identified by a clientId.

Pause / Words you will see

A small decoder ring

Read these once, then return to the animated stories. The exact command names are useful when you open the code.

Docker container

A separate box running one program. This project has six: dashboard, proxy, API, Redis, worker, and alerter.

Baileys socket

One active WhatsApp connection for one account. The worker creates and manages it using the Baileys library.

Session

Saved login files. With a valid session, an account can reconnect without scanning a new QR code.

Redis key

A named place in Redis where the system keeps data, such as one client’s status or waiting messages.

Queue · LPUSH · BRPOP

A waiting line. LPUSH adds a message; BRPOP takes the next one when the worker is ready.

Stream · XADD · XACK

An update feed. XADD posts an update; XACK marks it handled. QR and connection updates use this feed.

WebSocket

A long-lived browser connection. A subscribed app can receive new status and QR updates without asking again.

JID

WhatsApp’s address for a recipient. The worker turns a phone number into this format before sending.

DLQ · dead-letter queue

A holding area for broken stream updates that repeatedly fail. The outbound message queue has no such holding area.

Hash · list · set

Redis data shapes: a hash is a small table, a list is an ordered line, and a set is a collection with no duplicates.

Sorted set · TTL

A sorted set keeps items ordered by a number, such as time. TTL means data disappears automatically after a set period.

API route · GET · POST

A route is an address for an action. GET asks for information; POST asks the system to create or do something; DELETE removes something.

Webhook

A secret web address that lets a program post into one Google Chat space. Anyone holding it can post there, so it lives only in .env.

Environment label

Which CRM setup — dev, test, UAT or prod — uses an account. The API learns it from who is calling, never from the account’s name.

05 / What to remember

Rules that affect real messages

These are the most useful facts when something seems stuck or when you change the code.

SENDING

Messages wait for a connection

A request to send only puts a message in line. The worker takes the next message when that account is connected, sends one at a time, and waits a random interval after a successful send.

FAILURES

A failed send is tried again

The message returns to the same waiting line if sending fails. There is no built-in limit on how many times this can happen. If an invalid phone number somehow reaches the worker, it records the failure and discards that job.

UPDATES

Broken updates go aside

Connection and QR updates use a separate feed from outgoing messages. If the API repeatedly cannot read an update, it puts that update in a problem area for investigation.

HISTORY

Recent and long-term records differ

Redis keeps about seven days of message results. A separate file stores longer-lived history until someone deletes it. Deleting an account does not immediately remove its recent message results.

ACCESS

Protect the API separately

The management website asks for a password, but the API and live-update connection have no built-in login check. Anyone who can reach them may be able to create, send, or delete.

DASHBOARD

Status is refreshed every five seconds

The dashboard asks the API for fresh status every five seconds, and stops asking while its browser tab is hidden. It uses the live-update connection only for the “Show QR” window, so the QR refreshes by itself.

ALERTS

Only watched accounts alert

The alerter posts to Google Chat only for accounts switched on with “Watch for alerts.” If the whole server or the alerter is down, nothing can alert — a missing daily “all OK” message is the sign. Without a webhook it only writes to its own log.
