★ Start here

The whole system, no jargon

Read this section first if any of BRPOP, XADD, JID, or "consumer group" mean nothing to you yet. Everything below still holds — this is just the same ideas in plain words before the technical detail.

What is Baileys?

A library that lets a normal Node.js program log into WhatsApp the same way the WhatsApp phone app does — no official Business API account needed. You scan a QR code once, and from then on the program can send and receive messages as that phone number.

What is a "socket" here?

One open, logged-in connection to WhatsApp for one phone number. Think of it like a phone call that's been left connected — as long as it's open, that number can send messages. Each client (each phone number the system manages) gets its own socket.

Why is Redis everywhere?

Redis is a shared whiteboard both api and worker can read and write. Instead of the two programs calling each other directly (which gets messy and fragile), api writes a note on the whiteboard ("please connect client-1") and worker checks the whiteboard and acts on it. Neither has to know the other is even running.

What is "the queue"?

A waiting line for outgoing messages, stored in Redis. When you ask the system to send a message, it doesn't send right away — it joins the line for that phone number. A dedicated helper process for that number pulls messages off the front of the line one at a time, but only while that number is actually connected.

How does the dashboard "see" status in realtime?

Your browser keeps one connection open to the api (a WebSocket — like a phone line, not a series of phone calls). Whenever the worker changes a client's status (connecting, QR ready, connected, etc.), that change gets relayed down the same open line, so the page updates itself without you refreshing.

Why split "api" and "worker" at all?

Holding a live WhatsApp socket open is fragile — it can crash, disconnect, or need a QR rescan. Keeping that risky work in one dedicated process (worker) means the public-facing api can be restarted, redeployed, or scaled without ever dropping a live WhatsApp session.

Jargon, decoded

You'll see these Redis and messaging terms throughout the rest of this doc. Come back here if you lose the thread.

TermIn plain English
LPUSH / RPUSHAdd an item to one end of a waiting list stored in Redis (left end / right end).
BRPOP"Wait here until something shows up in this list, then take it." Used so the sender loop doesn't have to keep checking — it just sleeps until there's work.
XADD / streamAdd an entry to an append-only log (a Redis Stream) that multiple readers can each track their own read-position in — like a group chat's message history.
Consumer groupA named "reading position bookmark" on a stream, so if the reader process restarts, it knows exactly where it left off instead of re-reading everything or missing entries.
XACK"I successfully handled this stream entry, you can stop tracking it as unfinished."
DLQ (dead-letter queue)A side list for entries that repeatedly failed to process — a way to set them aside instead of retrying forever or silently losing them.
JIDWhatsApp's internal address format for a chat, e.g. 91999999999@s.whatsapp.net — the phone number plus a suffix saying what kind of chat it is.
TTL"Time to live" — how long a piece of data is allowed to sit in Redis before it's automatically deleted.
MIME typeA short label describing what kind of file something is (e.g. image/jpeg, application/pdf), used here to decide whether a file can carry a text caption.
01 · Mental model

Three flows, not one big pipeline

Nearly everything the system does decomposes into one of three flows. Internalize these and the rest of the codebase reads as detail, not surprise.

① Client lifecycle

api writes a command → worker starts or mutates a socket → worker writes state + publishes an event → api's stream consumer broadcasts it to subscribed WebSocket clients.

② Outbound message

api validates input → LPUSH onto wa:pending:<clientId> → worker's per-client sender loop blocks on BRPOP until the client is connected → dequeues and sends exactly one job at a time.

③ Realtime event

worker XADDs status/QR events to wa:events:stream → api's consumer group validates + XACKs → valid events broadcast through wsHub to client-scoped WebSocket subscribers.

02 · Service map

Five containers, one Redis

Every service is a thin, single-purpose process. None of them contain business logic that spans more than one of the three flows above.

In short: five small programs, each doing one job — worker talks to WhatsApp, api talks to the outside world, dashboard gives a human something to click, proxy handles HTTPS, and redis is the shared memory all of them read and write to.

worker owns every socket

Listens on wa:commands (BRPOP), initializes one Baileys socket per clientId, tracks connection lifecycle, publishes QR/status events, runs a dedicated sender loop per client, clears session files on logout/reset.

  • Entryworker/index.js
  • Coreworker/socketManager.js (759 lines — read this first)
  • Startupworker/startupRehydrate.js rebuilds sockets after a restart

api the only public surface

Fastify app exposing REST + GET /ws. Validates and enqueues; never opens a Baileys socket. Also runs the Redis Streams consumer that fan-outs events to WebSocket subscribers.

  • Entryapi/index.js — registers websocket, cors(origin:true), routes, starts stream consumer
  • CORSpermissive by design today — see §10

dashboard ops console

React SPA + a small Express server. The server does two things beyond serving static files: an HTTP Basic Auth gate, and a Docker-socket-backed GET /api/logs?service=&tail= endpoint for worker/api/redis/dashboard containers — wired and working server-side, but not currently called by anything in the React UI. See §09 for a full usage walkthrough.

  • Authbasic-auth, DASH_USER/DASH_PASS (default admin/admin, compose sets pass to change-me)
  • Dockermounts /var/run/docker.sock read-write to tail logs

proxy nginx TLS edge

Only container publishing 443 to the host (besides dashboard's 8080). Terminates TLS, proxies / and /ws to api:3000 with upgrade headers and 3600s read/send timeouts for long-lived sockets.

Redis — not just a cache

Redis is the command bus, the queue store, the state store, the QR cache, and the event stream — all five. Compose hardens it deliberately: requirepass, maxmemory 140mb with volatile-lru eviction, AOF persistence (appendfsync everysec), and no host port mapping — a comment in docker-compose.yaml notes an earlier config exposed 6379 to the internet and got its dataset wiped via REPLICAOF hijack. It is only reachable inside the compose network today.

The state machine, exactly as coded

Every transition below is taken from worker/socketManager.js's connection.update handler and the four command handlers. Click a state to see what the worker actually does on entry — Redis writes, published events, and what triggers the next hop.

In short: every WhatsApp connection moves through a fixed set of stages, like a traffic light — created, connecting, waiting for a QR scan, connected, disconnected, logged out, or manually stopped. The worker reacts differently depending which stage a client is in, and Redis always holds the current stage so any process can check it.

04 · Outbound message queue

The single most important contract in the system

POST /messages/send never sends anything. It validates and pushes a job onto a per-client Redis list. A dedicated sender loop per client is the only thing that ever calls sock.sendMessage.

In short: asking the system to send a message just joins a waiting line — it doesn't send instantly. A separate helper for that specific phone number works through its own line, one message at a time, and only while that number is actually connected. If a send fails, the message goes back to the front of the line and gets tried again later.

Enqueue — api/routes/messages.js

Validation, in order: clientId non-empty string · phoneNumber present and normalizes via libphonenumber-js (tries international parse first, falls back to region IN) · files must be an array, each needs non-empty file_url + mimeType · at least one of trimmed text or files must exist.

LPUSH wa:pending:<clientId>
{
  "type": "SEND_MESSAGE",
  "clientId": "client-1",
  "phoneNumber": "919999999999",  // e164, no +
  "text": "hello",
  "files": []
}

A queueUpdate event with the new list length is broadcast directly through wsHub — this one bypasses the Redis Stream entirely.

Dequeue — worker/socketManager.js: startSenderLoop

One loop per client, started as soon as initClient runs (even before connection) so nothing is missed after a worker restart. Each loop owns a dedicated ioredis connection — BRPOP blocks, and one blocking connection can't be shared across clients.

loop:
  if (!sock || !connectedClients.has(id)):
      sleep(2000); continue        // never dequeues while disconnected
  BRPOP wa:pending:<id> 0          // blocks until a job exists
  jid = toJid(phoneNumber)         // bad number → log "failed", DROP (not requeued)
  send via sendMessageWithMedia()
  on success: logMessage(sent); sleep(random(minMs,maxMs))
  on failure: logMessage(failed, failReason); RPUSH job back; sleep(3000)

What "reliable" actually means here

Sequential, always

One job in flight per client. No parallel sends, no fan-out — a slow send simply delays the next dequeue.

Requeue on send failure

A thrown error from sock.sendMessage RPUSHes the raw job back onto the same list, which — since consumption is BRPOP from the tail — makes it the very next item retried. No counter, no cap: it retries forever.

Invalid phone ≠ retry

A number that fails toJid() normalization is logged as failed and dropped permanently — it never reaches sock.sendMessage, so it is not requeued. This is a real distinction from "send failure."

Send delay — wa:config:sendDelay

After every successful send the loop sleeps randomBetween(minMs, maxMs) before the next BRPOP. Config is read fresh every cycle from Redis; both API and worker independently clamp and validate it the same way, so a malformed value in Redis can never break the loop.

default3000ms – 8000ms
allowed range500ms – 120000ms (clamped)
fallback triggerkey absent, unparsable JSON, or min > max

06 · Realtime event pipeline

From a Baileys callback to a browser repaint

Four hops, each with its own failure handling. This is the path QR codes and connection-state changes travel.

In short: think of it like a newspaper subscription. The worker publishes a headline ("client-1 is now connected") to a shared feed in Redis. The api reads that feed and, if the headline is valid, delivers it straight down the open WebSocket line to whichever browser tab is watching that client — usually within milliseconds.

1 · Publish — worker: publishEvent()

XADD wa:events:stream MAXLEN ~ 10000 * data <json> over a dedicated publisher connection, raced against a 10s timeout. Retried once on failure for QR events specifically.

2 · Consume — api/streamConsumer.js

Consumer group api-consumers, stable consumer name api-main (env WA_EVENTS_CONSUMER_NAME) — stable on purpose, so a restarted API reclaims its own pending entries immediately instead of waiting on cross-consumer autoclaim. Safe because compose runs exactly one api container.

3 · Validate + ack

A message is valid only if it has a data field, that field parses as JSON, and the parsed object has both clientId and type. Valid → broadcast then XACK. Invalid → failure counter increments in-memory, keyed by message ID.

4 · Poison → DLQ

After WA_EVENTS_POISON_THRESHOLD (default 5) failed attempts, the message is copied to wa:events:dlq and then acked off the main stream anyway — it will never block the pipeline. Caveat: failure counters live in a JS Map, so an API restart resets a message's strike count to zero.

Recovery on restart

On boot the consumer runs processPendingMessages() (own pending entries from id 0) then claimAndProcessStalePendingMessages() (XAUTOCLAIM, min-idle 10000ms, batch 50) before entering the main XREADGROUP BLOCK 1000 loop. The main loop re-runs autoclaim every 15000ms so a stalled/restarted consumer's entries are never stuck until the next deploy. If the consumer group itself vanishes (NOGROUP — usually a Redis wipe), it's recreated from '0', not '$', so nothing written during the gap is silently skipped.

WebSocket delivery — GET /ws

The first inbound message on a socket must include clientId; that's what subscribes it via wsHub. Every (re)subscription pushes an immediate snapshot: current state from wa:clients:state plus queueCount and, if present, the live QR. Ping frames get a pong and a fresh snapshot resync — deliberate self-healing against any broadcast that got dropped in transit.

→ {"clientId":"client-1","type":"ping"}
← {"type":"pong","timestamp":1710000000000}
← {"type":"status","clientId":"client-1","state":"CONNECTED","queueCount":0}

08 · API reference

Every route, exactly as validated

All routes live under api/routes/. None require authentication at this layer — see §10.

Client lifecycle
GET/clients

Returns the raw wa:clients:state hash — every known clientId and its state, unfiltered.

POST/clients/:clientId

Validates clientId against ^[a-zA-Z0-9._:-]{1,120}$. Returns 409 if the client already exists — no state reset on conflict.

200 { ok: true, clientId }
409 { error: "Client already exists", clientId, state }
400 { error: "Invalid clientId format" }

Writes CREATED to the state hash, then enqueues ADD_CLIENT.

POST/clients/:clientId/reconnect

Gatekept: only allowed from LOGGED_OUT, DISCONNECTED, or STOPPED. Enqueues ADD_CLIENT.

400 { error: "Client must be LOGGED_OUT, DISCONNECTED, or STOPPED" }
POST/clients/:clientId/restart

Body: { resetSession?: boolean }. Enqueues RESTART_CLIENT — tears down the socket, optionally wipes session files, immediately reinitializes.

POST/clients/:clientId/stop

Body: { resetSession?: boolean }. Enqueues STOP_CLIENT — tears down the socket, sets state STOPPED. No auto-reconnect.

DELETE/clients/:clientId

Enqueues DELETE_CLIENT — removes the state hash field, session files, QR key, pending queue. Publishes a DELETED event (event-only, never a persisted state). wa:msglog history is deliberately preserved.

GET/clients/:clientId/status 
200 { state: "CONNECTED" }
200 { clientId, state: "NON_EXISTENT" }   // when unknown
Queue & messages
POST/messages/send

Body: { clientId, phoneNumber, text?, files? }. Validates and LPUSHes onto wa:pending:<clientId> — see §04 for the full contract.

200 { ok: true, queued: true }
400 { error: "Missing fields" | "Nothing to send" | "files must be an array" | ... }
GET/clients/:clientId/queue?limit=1-200 
{ clientId, total, returned, limit, messages: [{ index, raw, parsed }] }
DELETE/clients/:clientId/queue

Drops the entire pending list and broadcasts a queueUpdate event with count 0.

GET/clients/:clientId/messages/log?limit=&before=

Reads wa:msglog:<clientId>, newest first. limit 1–200 (default 50). before is a Unix-ms cursor (default +inf).

09 · Using the dashboard

What you actually see when you open it

The dashboard is a single-page React app at :8080, sitting behind its own HTTP Basic Auth, that talks to api over plain REST — it never touches Redis or a Baileys socket directly. Everything below is read straight from dashboard/src/App.jsx, not the README's description of it.

In short: one scrolling page, no sidebar, no tabs. A header with a login-gated API endpoint field, four small cards for overview/create/test-send/config, and one list of every known client with buttons that pop open a modal for that client's queue, logs, or history.

Getting in

1 · Basic Auth

Visiting :8080 immediately prompts for a username/password — this is dashboard/server/index.js's authMiddleware, checked against DASH_USER/DASH_PASS. Code default is admin/admin; compose overrides the password to change-me but leaves the username as admin. Change both before any real deployment.

2 · Point it at the right API

Once past auth, the header has an "API Endpoint" text field, defaulting to http://localhost:3000. It's saved to localStorage under the key apiBase automatically as you type — there's no separate save button. If it's wrong, there's no error banner: every request just fails silently (only logged to the browser console), so the counters and client list quietly stop updating. If nothing on the page seems to move, check this field first.

The four top cards

System Overview

Three numbers: Known Clients, Active Sockets, WS Connections — pulled from /debug/client-states, /debug/active-clients, and /debug/ws-stats respectively.

Create New Client

One text field (e.g. client-123) and a Create button, disabled only while the field is empty. Submits POST /clients/:id with no body. The server-side clientId format check (^[a-zA-Z0-9._:-]{1,120}$) isn't mirrored in the form — an invalid ID just surfaces as a generic failed-request error.

Send Test Message

Client ID, phone number, and message text — three plain fields, text only, no file/media inputs in this form. Queue Message submits POST /messages/send with files: []. No confirmation and no success toast; the fields just clear, which is the success signal.

Send Delay

Min ms / Max ms number inputs plus a line showing what's actually active right now: Active: {minMs}ms – {maxMs}ms · source: default|redis. Save posts to /config/send-delay; the button relabels to "Saving…" while in flight.

The client list

One row per known client, sorted alphabetically by ID (not by state or activity). Each row shows a state badge (Created / Connecting / Scan QR / Connected / Disconnected / Logged Out / Stopped, or the raw state string if something unrecognized shows up), a ● Live badge if the client currently has an active socket, and a {n} WS badge showing how many open WebSocket subscribers are watching it right now.

  • View groupQueue · Logs · History — each opens its own modal for that client (see below). These are three separate buttons, not tabs inside one panel.
  • Control groupReconnect · Restart · Reset+Restart ("Wipe WhatsApp session then restart") — all fire immediately on click, no confirmation dialog.
  • Stop groupStop · Reset+Stop ("Wipe WhatsApp session then stop") · Delete. Only Delete asks first: Delete client "{id}"? This cannot be undone. Stop and Reset+Stop fire immediately, same as the control group.

Careful with this: Reconnect, Restart, Reset+Restart, Stop, and Reset+Stop all execute the instant you click them. Only Delete, Clear Queue (inside the Queue modal), and Delete File (inside the History modal) ask window.confirm first. A misclick on Reset+Restart silently wipes a session with no undo prompt.

The three modals

Queue

Loads GET /clients/:id/queue?limit=100. Shows pending count, each entry's index/type/phone/file-count/text, a Refresh button, and Clear Queue (confirms first, then DELETE .../queue). Empty state: "Queue is empty — no pending messages."

Logs

Loads GET /clients/:id/messages/log?limit=100 — the 7-day rolling wa:msglog history. Sent/failed status badge per row, failReason shown on failures. Footer reminder: "Logs auto-expire after 7 days." Refresh only, no date filtering.

History

Loads GET /clients/:id/logs/persistent — the on-disk .jsonl mirror, with actual from/to date-range inputs (defaulting to today) and a Load button. Also has Delete File (confirms, then permanently deletes that client's log file). Footer note: "Persistent logs have no TTL" — unlike the 7-day Logs modal.

There's also a standalone lookup field above the client list — "Look up any client queue by ID…" — for checking the pending queue of a clientId that isn't in the known-clients list yet (e.g. one that was only ever enqueued to, never created). It only opens the Queue modal — there's no equivalent manual lookup for Logs or History.

  • Not actually realtimeThe whole dashboard runs on a plain setInterval(refreshAll, 5000) — a 5-second REST poll of the debug endpoints. It never opens GET /ws itself, despite that endpoint existing for exactly this purpose. A state change can take up to ~5s to show up here, unlike a page using the WebSocket directly.
  • Container log tailing isn't wired up yetdashboard/server/index.js exposes a working GET /api/logs?service=worker|api|redis|dashboard&tail=<n, capped 2000> backed by the mounted Docker socket — but nothing in the current React UI calls it. The backend capability described in §Docker above exists and works if you hit it directly; there's just no button for it today.
10 · Deployment topology

Docker, and how this repo uses it

The whole stack runs as Docker containers, wired together by docker-compose.yaml. If Docker itself is new to you, start with the plain-English version below; the rest of this section is the specifics of this repo's setup.

Container

A running process boxed off from the host and from every other container — its own filesystem, its own installed packages, its own view of "localhost." worker can crash or leak memory without touching api's process at all.

Image

The frozen recipe a container is started from — built once by a Dockerfile (install Node, copy source, set the startup command), then reused every time that container starts or restarts.

Volume / bind mount

A folder that lives outside the container and survives even if the container is deleted and recreated. This repo uses this deliberately for anything that must not vanish on a rebuild — see "things to remember" below.

In short: docker-compose.yaml is the wiring diagram — it says which five images to build, what to name each running container, which folders to mount into which container, which ports reach the host machine, and which containers must be healthy before another one is allowed to start. Only two ports reach the host; everything else — including Redis and the API's own port 3000 — stays inside the private compose network.

proxy 443 → host

nginx:1.27-alpine. TLS via nginx/certs/origin.{crt,key}. Proxies / and /ws to api:3000, 3600s timeouts for the websocket route.

dashboard 8080 → host

Mounts /var/run/docker.sock to tail container logs. 100M memory limit.

api 3000 · internal only

Mounts ./logs:/logs. Depends on redis being service_healthy. 100M memory limit — it's a thin router.

worker no ports

Mounts ./sessions:/sessions and ./logs:/logs. 1G memory limit — Baileys sockets + Signal state add up per client. Liveness heartbeat file at /tmp/worker-heartbeat, rewritten every 30s.

redis no host port, by design

requirepass + maxmemory 140mb volatile-lru + AOF appendfsync everysec + save 60 1000 + maxclients 100. Data in named volume redis-data.

How each image gets built

All three app images (worker, api, dashboard) start from node:20-alpine — the small Alpine Linux variant of the official Node image.

worker/Dockerfile

Single stage: install deps, copy source, run. Node's heap is capped at 512MB via --max-old-space-size on the start command — set as a node flag, not NODE_OPTIONS, so a bad flag fails loudly at startup instead of the container silently crash-looping. A HEALTHCHECK reads the heartbeat file worker writes every 30s and fails the container "unhealthy" if it's gone stale.

api/Dockerfile

Same single-stage pattern as worker, no HEALTHCHECK defined — compose only waits on redis's healthcheck before starting api, not the reverse.

dashboard/Dockerfile

Two stages. Stage one installs deps and runs npm run build to compile the React app. Stage two starts from a fresh node:20-alpine and copies over only the built dist/, the small Express server/, and node_modules — the React build toolchain itself never ships in the final image.

Things to remember when working with this stack

  • Sessions live outside the imageWhatsApp login state is bind-mounted at ./sessions, not baked into the worker image. Delete or lose that folder and every client has to scan a fresh QR — rebuilding or recreating the worker container does not do this by itself, but wiping the mount does.
  • Don't reach for -v casuallydocker compose down is safe — named volumes and bind mounts survive. docker compose down -v also deletes the redis-data volume, which throws away client state, queues, and the send-delay config (though not the session files themselves, since those are a bind mount, not a volume).
  • Rebuild only what changedAfter editing one service's code: docker compose up -d --build worker (or api/dashboard) rebuilds just that image and restarts just that container — no need to take down the whole stack.
  • The 1G worker limit is a ceiling, not a targetNode's own heap is capped at 512MB, but Baileys/Signal state, buffered media, and native memory sit outside the JS heap — real usage climbs with concurrent connected clients. Watch this if you add more clients than the stack was sized for.
  • service_healthy gates startup orderBoth worker and api wait for Redis's healthcheck (a redis-cli ping) before starting — not just for the Redis container to exist. If Redis is slow to come up, dependent containers wait rather than crash-looping against a closed connection.
  • Cert rotation needs a forced recreateNginx reads the mounted cert files once at container start. After replacing nginx/certs/origin.{crt,key}: docker compose up -d --force-recreate proxy — a plain restart of the stack won't necessarily pick up new files depending on how they were replaced.
  • The dashboard's Docker socket mount is real host access/var/run/docker.sock is mounted into the dashboard container so it can tail other containers' logs — but that socket is effectively root-equivalent control over the whole Docker host. Treat dashboard credentials with the same seriousness as host SSH access, not just "an admin panel password."
  • Redis has no host port on purposeThe compose file's own comment explains why: an earlier config published 6379 to the internet and an unauthenticated REPLICAOF hijack wiped the dataset repeatedly. Don't add a ports: mapping back onto the redis service.

Session storage — what's actually in /sessions

In short: a "session" is WhatsApp's saved login for one phone number — the cryptographic keys that let the socket reconnect silently instead of asking for a fresh QR scan every time. It lives as plain files on disk, one folder per clientId, mounted in from outside the container so it survives restarts and rebuilds.

How it's created and read

Baileys' own useMultiFileAuthState(sessionPath) — called in initClient() against /sessions/<clientId> — creates the folder on first connect if it doesn't exist, and hands back a state object plus a saveCreds() callback that socketManager.js wires to Baileys' creds.update event so every credential rotation is persisted immediately, not just on clean shutdown.

What's actually in the folder

Not one file — many small ones, one JSON file per stored key: creds.json (the account identity), plus a growing set of pre-key-*.json, session-*.json, sender-key-*.json, app-state-sync-key-*.json and app-state-sync-version-*.json files as the Signal protocol negotiates keys with each chat. Every read/write is guarded by an in-process file lock, so concurrent credential updates can't corrupt a file mid-write.

  • creds.json is the crown jewelIt holds the account's identity and signing keys. Lose only this file and the effect is identical to a full logout — a fresh QR scan is required. The other files are protocol bookkeeping that Baileys rebuilds automatically as conversations resume.
  • These files ARE the login — treat them like credentialsAnyone with read access to /sessions/<clientId> can impersonate that WhatsApp number without ever seeing a QR code. There's no password layered on top of the filesystem permissions. Back it up encrypted if at all, and never commit it, log it, or ship it in a support bundle.
  • Deleted wholesale, never partiallyworker/sessionUtils.js: clearSession() does a recursive delete of the whole /sessions/<clientId> folder. It runs automatically on LOGGED_OUT (a fresh QR is coming anyway) and on any restart/stop/delete called with resetSession: true. Ordinary disconnects and reconnect backoff never touch these files — that's why a transient network blip doesn't force a rescan.
  • The bind mount is the only thing making sessions durableCompose mounts ./sessions:/sessions on the worker (see §Docker above) specifically so this folder outlives container rebuilds. If that mount is ever missing or points somewhere new, every client looks freshly logged-out on next start — the code has no fallback location.
  • A real path inconsistency to know aboutworker/startupRehydrate.js honors WA_SESSIONS_DIR (default /sessions) when scanning which clients to rehydrate on boot — but socketManager.js's initClient() and sessionUtils.js's clearSession() both hardcode the literal string /sessions/<clientId>. Setting WA_SESSIONS_DIR to anything else without also moving the bind mount will make startup rehydration scan the wrong folder while live reads/writes keep hitting /sessions.

11 · Known gaps

Current realities, not future tickets

Pulled directly from AGENTS.md §19 and cross-checked against the code. These are operational facts to design around, not bugs waiting for a PR.

HIGH
API and WebSocket endpoints are unauthenticated.

Anything that can reach api:3000 — directly, or through the nginx proxy — can create, message, or delete any client. The dashboard's Basic Auth only gates the dashboard's own Express server, not the API itself.

MED
CORS is fully permissive (origin: true in api/index.js).
MED
Redis host is hardcoded to "redis" in most modules; only api/streamConsumer.js respects REDIS_HOST. Inconsistent if the topology ever changes.
MED
No outbound retry counter or DLQ. A send that keeps throwing retries forever, 3s apart, with no ceiling and no place to route it out of the loop.
MED
Poison-message counters are in-memory only in the stream consumer — an API restart resets every message's strike count to zero.
MED
Bare phone numbers default to India (+91). Both worker/phone.js and api/phone.js — byte-for-byte identical files — fall back to region IN when a number can't be parsed as international.
MED
Dashboard default credentials are baked into code (admin / admin). Compose overrides the password to change-me but leaves the username default.
12 · Cookbook

Common operations

Copy, adjust the host/clientId, run. Assumes the self-signed origin cert, hence -k.

Create a client

curl -k -X POST https://localhost/clients/client-1

Check status

curl -k https://localhost/clients/client-1/status

Queue a text message

curl -k -X POST https://localhost/messages/send \
  -H "content-type: application/json" \
  -d '{"clientId":"client-1","phoneNumber":"9999999999","text":"hello"}'

View pending queue

curl -k "https://localhost/clients/client-1/queue?limit=20"

Clear a stuck queue

curl -k -X DELETE "https://localhost/clients/client-1/queue"

Recent message log

curl -k "https://localhost/clients/client-1/messages/log?limit=100"

Force a fresh QR (logged out / stuck)

curl -k -X POST https://localhost/clients/client-1/restart \
  -H "content-type: application/json" \
  -d '{"resetSession": true}'

Run the test suites

cd api && npm test
cd worker && npm test
